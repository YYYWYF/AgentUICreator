# UI-system selection for new visual Plugins

Applicability: creating a new visual Plugin or making a real UI-system choice.
Existing application edits preserve their selected system and use its public
contracts; they do not reopen this selection without contradictory evidence.
This reference defines evidence and boundaries, not an ordered tool workflow.

Choose from the actual target page's rendered controls, established Host system,
existing public primitives, then necessary approved dependencies. Package presence
or import counts alone do not decide. Host wrappers and direct library controls
are both valid when they are what the page uses. Do not replace them merely
because a different Agent UI control is familiar.

Host uiContext supplies direct dependencies/scripts and navigation. Inspect the
relevant page, exports and reachable Provider/theme when those facts are needed.
A nearby Plugin can establish registration/locale conventions; it is not another
required consumer proving an npm API. Use installed public contracts rather than
searching node_modules, Runtime or generated files. Source Items are relevant for
missing formal resources, not an obligatory detour for supported public controls.

For new panel/semantic-slot plans, componentBasisRefs contains real inspected UI
selection paths; reuseEvidenceRefs describes capability reuse. Bind the plan to
actual imports, Provider/theme and the chosen UI system. Refresh stale evidence
when the Host requires it. Do not fabricate references or treat admission as
permission to change another layer.

A new side panel must fit its actual Layout, tracks, existing dimensions and
responsive container. Preserve requested placement and usable Composer space;
use existing Layout collapse controls instead of hiding content while leaving
its reserved track occupied. Ask about layout only if a material choice remains.
A project-local dialog/form does not imply a new side panel or AppUIModel Slot.

Use public styled controls/overlays with their existing theme/container boundary.
Consult returned presentation contracts for style assets and whether a composite
owns its Portal/Backdrop. Native semantic structure is fine; avoid a parallel
control system. Scoped CSS may adapt owned surfaces without global resets.
For nested dialogs verify topmost Escape behavior, focus containment and return
to the opening control in the actual Host. Public types do not establish this.

After mutation use current-revision static/build and policy-required Runtime
validation. New Plugin placement/delivery obligations are in authoring-contracts.md.
Browser evidence for requested geometry and interactions remains separate; absent
infrastructure or unavailable evidence must be reported honestly.
