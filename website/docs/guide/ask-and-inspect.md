# 提问、检查工程与先做方案

Creator 可以解释用法、读取工程现状或提出改造方案。想先讨论时，在需求里直接说明「先不要修改文件」。

## 选择请求方式

| 目标 | 可以这样说 |
| --- | --- |
| 了解使用方法 | 「如何在业务页面放入助理？请解释步骤。」 |
| 核对工程现状 | 「检查当前启用了哪些 Plugin，列出对应应用层文件，暂不修改。」 |
| 比较方案 | 「准备把侧栏变窄，先给出布局调整方案、影响范围和验证方法。」 |
| 排查现象 | 「发送按钮不可用，先检查启用状态、组合和必要服务，不修改代码。」 |

需要工程事实时，Creator 会按需检查项目。纯使用问题不应以扫描整个仓库为前提。不要把一份建议当成已经执行的代码变更。

## 让方案可以审查

说明希望改变的区域、要保留的行为、目标效果和验收条件。例如：「仅改变右侧内容宽度，保留会话列表和消息输入；窄屏不出现横向滚动。」

收到方案后，核对它是否区分了布局、Plugin 应用层和实现源码。布局通常改 AppUIModel；props、children 和 renderer 在项目应用层修改；源码接管要有单独的具体计划和同意。

需要继续实施时，明确告诉 Creator 采用哪个方案。运行中出现问题卡片，就在卡片里回答；若方案范围变化，重新核对将改动的文件。

## 确认只读结果

只读咨询可以只返回解释，不一定附带修改回执。检查请求应说明观察到的文件或状态、仍不确定的部分和下一步证据。没有文件差异、没有安装操作，才符合「先不修改」的要求。

> 截图待补：同一工程的一次只读检查，显示用户明确不修改、Creator 的发现和建议，画面中不出现虚构的修改成功状态。

确定要实施后，继续[通过对话修改界面](./request-changes)。
