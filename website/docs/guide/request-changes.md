# 通过对话修改界面

开始前确认当前工程正确、Creator 模型可用，并能打开工程自己的开发页面。Creator 会根据任务选择读取、编辑和验证方法，每次任务不要求经过相同的固定步骤。

## 描述一个可验证的修改

一次请求写清目标、范围和保留项。例如：

> 将会话列表宽度调小一些，让对话区占更多空间。保留新建会话、列表搜索和所有消息交互，窄屏下不能横向溢出。先检查当前布局，再修改并运行相关检查。

其他常见请求包括修改主题、调整布局尺寸、组合已有 Plugin、替换应用层 renderer。组件支持的公开参数优先在薄应用层传入，不必为普通外观调整先复制官方实现。

## 审查需要确认的内容

阅读问题卡片中的对象与范围，再确认。新增依赖、源码接管、依赖升级、源码同步与基线采用有各自的授权边界；一条「调整颜色」请求不能自动变成接管全部 Plugin 的同意。

想收窄范围可以回复：「只改应用层，不接管实现；保留现有依赖版本。」如果现有公开接口不足，先查看替代方案与具体接管计划。

## 查看结果并验收

1. 核对回复、文件差异及[验证回执](./receipts-and-validation)。
2. 回到开发页面，比较修改前后的区域，检查正常状态、运行状态和窄屏。
3. 运行工程已有的 `test`、`typecheck`、`build` 脚本，按实际存在的脚本执行。
4. 需要继续调整时，描述具体剩余问题，并注明应保留的现有修改。

不要仅凭「构建通过」认定视觉效果符合需求。若回执只完成静态验证，页面交互仍要检查；没有可用浏览器时，也应保留未验证状态。

> 截图待补：同一工程同一视口下的修改前后对照，以及对应文件差异和检查结果；不要用不同预设代替修改效果。

不满意时按[撤销与重新应用](./undo-redo)处理可撤销事务，先检查后续手动修改是否会冲突。
