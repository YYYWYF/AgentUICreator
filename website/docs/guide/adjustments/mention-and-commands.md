# 自定义 @ 候选与 / 命令

描述要搜索什么、选中后做什么，Creator 再检查已有能力和缺少的资料。以下是 2026 年 10 月 27 日的实际请求与结果。

## 先询问员工搜索与工单命令

实际发送：

> 在助理输入框增加 @ 搜索员工，候选显示姓名和部门，数据来自现有员工搜索接口。选择后让 Agent 按员工 ID 获取资料。同时增加 /工单 命令，点击后将“查询我的待处理工单”填入草稿，由用户确认发送。请先说明需要我提供哪些接口信息，再完成接入。

Creator 首轮没有执行，反问是哪个功能或位置。

![本轮首轮回复，Creator 没有直接识别要修改的位置。](/images/guide/examples/20261027/mention-first-reply.png)

随后实际补充：

> 就是助手底部平时输入消息的那个框。输入 @ 时能搜索员工，输入 / 时能选择“查询工单”。先告诉我员工搜索还需要哪些资料，不要替我编接口。

Creator 检查后列出了员工搜索地址、请求与返回样例、登录方式和选中员工后传给 Agent 的内容等待补充信息。没有修改文件，最后仍显示任务未完成。**员工搜索并未接入。**

![Creator 列出缺少的资料，并保留任务未完成的实际结果。](/images/guide/examples/20261027/mention-info-reply.png)

## 再单独添加草稿命令

本轮继续发送：

> 员工搜索先不做。在助理的 / 菜单增加“查询工单”，选择后将“查询我的待处理工单”填入草稿，不立即发送。保留已有命令。

Creator 修改了七份项目文件，代码检查通过。期间它提出菜单短名和完整草稿文字的取舍；测试中选择了“用‘查询我的待处理工单’”，没有给代码或参数指导。

![Creator 的实际取舍问题。](/images/guide/examples/20261027/slash-question.png)

## 实际页面结果：部分完成

在浏览器输入 /，菜单确实出现，原有“新建会话”仍在。新菜单项的主文字变成了“查询我的待处理工单”，“查询工单”显示为说明。

![本轮实际打开的命令菜单。](/images/guide/examples/20261027/slash-menu.png)

选中后没有自动发送，但输入框里出现了带方括号和大括号的标记文字，**并不是要求的那句纯文本**。

![选中后的实际草稿，显示了标记文字；欢迎区仍在，未自动发送。](/images/guide/examples/20261027/slash-draft.png)

因此，本轮只能确认菜单和不自动发送的行为；原始短菜单名与纯文本草稿要求没有同时完成。不能把类型检查通过或 Creator 的完成回复当成整个需求成功。

接入员工搜索仍需实际服务资料。相关能力见[搜索对象](/plugins/mention-trigger)和[使用命令](/plugins/slash-command-trigger)。
