# 处理升级失败与恢复

恢复先识别失败阶段：发现/计划、依赖安装、实际身份检查、工程验证或源码合并。保留回执，不把所有状态统称「升级失败」。

## 依赖恢复

工具保存本轮声明、锁文件、实际解析版本和阶段，按恢复方案还原本轮声明/锁，再重新安装原依赖。检查结果必须覆盖实际 node_modules，单独恢复 package.json/lockfile 不足以证明安装恢复。

如果恢复失败，保留部分完成状态，查看可重试条件。不能覆盖升级期间其他人的新改动，也不能无范围删除锁文件或依赖。

## 外部效果与未知进程

生命周期脚本、缓存和外部服务可能有不可由文件回滚逆转的副作用。中断后不确定的安装进程需要人工检查其身份和状态，不能根据旧 PID 随意终止其他进程。

Windows 上文件可能被进程占用。先停止本任务确认拥有的进程，再重试受控清理；不以强制递归删除整个工程解决。

## 源码阶段

源码合并事务与依赖安装分别处理。合并失败保留旧源码基线；npm 已成功安装时如实报告。恢复应用层或实现前查看当前 diff，保护无关定制。

## 判断恢复完成

确认声明和锁文件、实际版本、受保护源码、源码基线 与项目检查结果都符合恢复计划。日志只保留必要路径、错误码和摘要，移除 token 与业务数据。
